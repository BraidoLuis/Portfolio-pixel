## Testes: método e limites

A contagem registra chamadas de definição `it`/`test`, expande tabelas `each` e executa apenas callbacks de declaração de suítes e loops de registro. Imports foram substituídos por stubs e os corpos de teste/hooks não foram executados. As declarações parametrizadas e loops foram conferidos no código. Loops internos de asserções não geram novos casos. A contagem considera definições por suíte, sem multiplicar por projetos/navegadores do executor. Nenhum arquivo apresentou falha de registro ao final.

Esta auditoria de projetos não executou suas suítes completas e não afirma aprovação, cobertura ou funcionamento dos provedores externos. Os checks locais do Portfólio são validados separadamente.

| Projeto | Definições verificadas |
| --- | --- |
| SPA Express | 486 Vitest + 30 Playwright = **516** |
| FriBolos | 434 Vitest + 1 node:test de fumaça de build = **435** |
| Meus Gastos | 14 bot + 12 dashboard/API + 1 backup com node:test; 15 Playwright = **42** |
| NB Arquitetura | 10 Vitest + 10 Playwright = **20** |
| Portfólio Pixel | **12 scripts** distintos: mundo 6, casa 3, personagem 2, links 1 |

O SPA possui também roteiro SQL e executor de regressão/concorrência PostgreSQL, separados dos 516 casos. No FriBolos, unidades, componentes e hooks são classificados por arquivo; não se atribui integração real a mocks. Nos demais projetos, ausência de suíte identificada não significa aprovação manual. Comandos herdados de templates também não comprovam testes autorais.

Classificação pelos arquivos: SPA tem 158 casos de regras/utilitários, 203 de
serviços com mocks e 125 de rotas com mocks no Vitest. FriBolos tem 106 unitários
(formatters, product-options, validator), 182 de componentes (incluindo o
carrossel de avaliações em supabase.test.tsx) e 146 de hooks. O painel mostra
essas divisões, sem classificá-las como integração real com os provedores.

## Divergências e maturidade

- SPA: serviços atuais consultam Supabase, apesar de observação antiga de dados demonstrativos no README. Resend, filas e crons têm implementação. WhatsApp possui links de contato/encaixe; a menção a Cloud API no README não demonstra um remetente implementado. Pagamentos são confirmados manualmente.
- FriBolos: frontend atual usa Vinext/Vite, React e TypeScript. Chamadas de Edge Functions para Stripe estão presentes; implementações externas de funções e webhook não estão neste repositório. E2E Playwright é evolução planejada.
- NB: administração com Supabase Auth/SSR, PostgreSQL, Storage e RLS efetivamente presente.
- BJJ: PaymentIntent/Elements para doação avulsa presentes; interface mensal referencia `/api/create-subscription`, ausente na árvore. Não há webhook versionado.
- SPE/SAPE: frontend estático com serviços vazios; botão de inscrição sem ação.
- Orçamento: página inicial e rotas; Computação contém título e Mecânica está vazia. Sem orçamento funcional.
- Sistema de consultas: login, pagamentos e parte dos dados são simulações/memória/localStorage.
- TCC YOLO: persistência MySQL existe como rotina, mas chamada no pipeline está comentada; vídeo/modelo referenciados não constam da árvore.
- ByLearn: exemplos apenas no README e retorno da média dentro do laço; descrito como estudo introdutório.
- Estudos YOLO incluem exemplos de terceiros; a descrição não atribui autoria exclusiva.
